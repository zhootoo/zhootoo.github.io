## 一、Virtual 的语义：为什么需要它

<!-- 从问题出发引出 virtual，而不是直接给定义 -->

### 1.1 静态绑定 vs 动态绑定

<!-- - 普通函数调用在编译期就确定调用目标（静态绑定/早绑定）
     - 需求：用基类指针/引用调用时，希望执行"实际对象"的版本（动态绑定/晚绑定）
     - 用一段"不加 virtual 时输出不符合预期"的代码引出问题 -->

```cpp
class Animal {
public:
    void speak() { std::cout << "..." << std::endl; }
};
// Animal* a = new Dog; a->speak();  // 输出的是 Animal 的版本，为什么？

```

### 1.2 加上 virtual 之后

<!-- - 对比代码：speak 声明为 virtual 后行为改变
     - 给出多态的定义：同一接口、不同行为，绑定推迟到运行期
     - 点出关键规则：通过基类指针或引用调用才触发动态绑定 -->

## 二、Virtual 的基本用法

### 2.1 虚函数的声明与重写（override）

<!-- - virtual 声明、派生类中自动为虚
     - override / final 关键字（C++11）：显式标注重写，防拼写错误
     - 重写(override) vs 重载(overload) vs 隐藏(hiding) 的区别，一张表格对比 -->

### 2.2 虚析构函数

<!-- - 通过基类指针 delete 派生类对象，若析构非虚 → 未定义行为/资源泄漏
     - 经验法则：作为基类使用的类，析构函数要么 public virtual，要么 protected non-virtual -->

### 2.3 纯虚函数与抽象类

<!-- - 纯虚函数：virtual void f() = 0; 定义"接口"
     - 抽象类不能实例化，派生类必须实现所有纯虚函数
     - 纯虚函数也可以有实现体（鲜为人知的点，可选） -->

### 2.4 协变返回类型（Covariant Return）

<!-- - 派生类重写时返回类型可以是基类返回类型的派生类，仍构成重写（可选小节） -->

### 2.5 虚继承（预埋伏笔）

<!-- - virtual 还能修饰继承方式，解决菱形继承问题
     - 注意：虚继承的实现机制和虚函数完全不同！这里只提一句，后文单独展开
     - 提示读者不要把"virtual 函数"和"virtual 继承"的实现混为一谈 -->

### 2.6 不能是虚函数的情况

<!-- - 构造函数为什么不能是虚的（先有对象才有 vptr）
     - 静态函数、内联函数（虚函数调用通常不被内联）等限制 -->

## 三、实现机制：vptr 与 vtable

<!-- 本章是文章核心，建议配内存布局图 -->

### 3.1 一个关键问题：运行期如何知道该调谁？

<!-- - 编译器必须把"调用哪个函数"的决定从编译期挪到运行期
     - 思路推演：如果由语言直接支持，需要哪些信息？
       1. 每个对象要携带"自己属于哪个类"的信息
       2. 每个类要有一张"函数入口地址表"
     - 引出 vptr（对象内）与 vtable（每个类一份） -->

### 3.2 虚函数表（vtable）的结构

<!-- - vtable 是编译期生成的静态数组，存放该类所有虚函数的地址
     - 通常还包括：RTTI 信息（type_info）、虚继承相关的 offset 等（依编译器而异）
     - 同一个类的所有对象共享一张 vtable；派生类的 vtable 由基类的拷贝而来，
       被重写的槽位替换成新地址，新增虚函数追加在后面
     - 建议画一张 Base/Derived 两张 vtable 的对照图 -->

### 3.3 对象内存布局：vptr 藏在哪里

<!-- - 含虚函数的类，编译器隐式给每个对象插入一个 vptr 成员（通常在对象头部）
     - sizeof 的变化：空类 1 字节 → 含虚函数 8 字节（64 位）
     - 用代码验证：打印 sizeof、成员偏移（offsetof 不可用于非标准布局，可用伪代码示意） -->

### 3.4 虚函数调用的完整过程

<!-- 一步步拆解一次调用的汇编级过程：
     mov rax, [rdi]        ; 取对象 vptr
     call [rax + offset]  ; 查表取函数地址并调用
     - 一次虚调用 = 2 次内存间接寻址
     - 所以构造函数不能是虚的：对象构造时 vptr 才由编译器写入
     - 虚函数调用默认不能内联（运行期才知道目标），除非编译器去虚化（devirtualization） -->

### 3.5 构造/析构期间的虚函数行为

<!-- - 构造派生类对象时：基类构造 → 派生类构造，vptr 逐步切换
     - 在基类构造函数中调用虚函数，调用的是基类版本（此时 vptr 指向基类 vtable）
     - 析构过程反向同理，这是经典陷阱 -->

### 3.6 多继承下的实现

<!-- - 有多个基类 → 对象内有多个 vptr，每个基类子对象各有一个
     - this 指针调整（thunk 技术）：通过第二个基类指针调用时需修正 this
     - 建议画多继承对象的内存布局图 -->

### 3.7 虚继承的实现

<!-- - 菱形继承下公共基类只有一份，位于（通常）对象尾部
     - 通过 vtable 中的 vbase offset 找到虚基类子对象
     - 解释虚继承下访问公共基类成员为什么更慢：多一层间接 -->

## 四、代价与工程实践

### 4.1 virtual 的开销清单

<!-- - 空间：每个对象 +8 字节（64 位下 vptr）；每个类一张 vtable
     - 时间：虚调用多 2 次内存访问 + 阻碍内联 + 分支预测不友好
     - 量化感受：绝大多数场景可忽略，但热循环/每对象数量巨大时需要注意 -->

### 4.2 什么时候不该用 virtual

<!-- - 不作为基类使用的类不要加虚函数（EBO：非虚类空基类可优化为 0 字节）
     - 对性能极致敏感的组件（如向量运算、ECS）常用 CRTP 静态多态替代 -->

### 4.3 替代方案与演进

<!-- - CRTP（静态多态）
     - std::variant + std::visit
     - C++20 concepts：面向接口编程不一定要继承
     - 编译器去虚化（devirtualization）与 final 的助益 -->
