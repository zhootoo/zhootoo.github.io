## 1. Cache 与 Cache Line

CPU 直接读内存（主存）太慢，所以中间加了几层高速缓存：**L1 / L2 / L3 Cache**。CPU 优先从缓存里取数据。

最关键的一点：

> **CPU 与 Cache 之间交换数据的最小单位是缓存行（Cache Line），主流 x86/ARM 上一般是 64 字节。**

换句话说：**CPU 不会单独读一个 4 字节的 `int`。** 只要你访问这个 `int`，CPU 会把它所在的**整整 64 字节**一次性拉进缓存。

假设两个变量 `x`、`y` 在内存里挨着放：

```
Cache Line（64B）
+--------+--------+--------------------------------------+
|   x    |   y    |             其余空间（无用）           |
+--------+--------+--------------------------------------+
 偏移0~3   偏移4~7
```

**x 和 y 落在同一条缓存行里**——这是后面所有故事的起点。

---

## 2. 伪共享的根源：MESI 缓存一致性协议

现代多核 CPU 里，**每个核都有自己独立的 L1 缓存**。多核同时读写同一块内存时，数据可能不一致，于是需要**缓存一致性协议**来兜底。主流方案是 **MESI**，它给每条缓存行定义了四种状态：

| 状态 | 含义 | 说明 |
| --- | --- | --- |
| **M**（Modified） | 已修改 | 我改了这条缓存行，别的核手上的副本全部失效 |
| **E**（Exclusive） | 独占 | 只有我有这份缓存行，主存还没被修改过 |
| **S**（Shared） | 共享 | 多个核都有这份只读副本 |
| **I**（Invalid） | 无效 | 我这边的副本作废，不能再使用 |

**MESI 的一条硬性规则（伪共享的关键）：**

> 一个核要**写**某条缓存行里的**任意一个字节**，必须先让**所有其他核**手上对应的缓存行副本全部置为 **Invalid（失效）**。

**注意：失效的单位是整条缓存行，不是单个变量！**
哪怕你只修改里面 4 字节的 `x`，整条 64 字节缓存行都会作废。

## 3. 完整场景还原：Core0 写 x、Core1 写 y

- **Core 0**：只写 `x`，从来不碰 `y`
- **Core 1**：只写 `y`，从来不碰 `x`

逻辑上：x、y 完全独立，**没有数据竞争，也不需要任何同步**。
但坏就坏在：**x 和 y 在同一条缓存行。**

{% asset_img false-sharing-mechanism.svg 伪共享失效循环机制图 %}

一步步走一遍：

**第 1 步：Core0 读取并修改 x**
1. Core0 读取 x → 把整条缓存行（含 x、y）拉进自己的 L1，状态 E（独占）
2. Core0 修改 x → 状态变成 M（Modified）

```
Core0 L1: [x, y]  M
Core1 L1: （无此缓存行）
```

**第 2 步：Core1 要修改 y**
1. Core1 本地缓存里**没有**这条缓存行，它向多核互连总线发起请求：*"我要写地址 &y 对应的缓存行"*
2. 这个请求在总线上**广播**，所有核都能"听到"（**嗅探 / snoop** 机制）
3. Core0 嗅探到这个地址，发现：*"这条缓存行在我手上，而且是 M 态！"*
4. 协议要求：M 态持有者必须把最新数据**写回主存**，然后把自己本地副本置为 **Invalid**，并回应总线
5. 总线把这份最新的缓存行数据交给 Core1，Core1 存入自己 L1，改成 E，然后修改 y → 变成 M

```
Core0 L1: [x, y]  I（失效！本地副本不能用了）
Core1 L1: [x, y]  M
```

**第 3 步：Core0 又要修改 x**
- Core0 发现自己本地缓存行是 Invalid，不能直接写
- 又要走一遍：通知 Core1 失效 → Core1 回写主存 → Core0 重新拉取整行 → 修改 x

**循环噩梦就这样形成了：**

```
Core0 写 x → 让 Core1 的整条缓存行失效
Core1 写 y → 让 Core0 的整条缓存行失效
Core0 写 x → 让 Core1 的整条缓存行失效
Core1 写 y → 让 Core0 的整条缓存行失效
……无限来回
```

这就是 **False Sharing（伪共享）**：

> 逻辑上：两个变量互不共享、互不依赖；
> 硬件上：它们共享了同一条缓存行，触发疯狂的失效、回写、重拉。

---

## 4. 关键疑问：Core1 本地没有 y，为什么会触发失效？

这是最容易困惑的一步。拆开说清楚：

> **Core1 的本地 L1 缓存里，确实没有 y 的副本。**
> 但 CPU 多核之间有一条共享的总线/互连链路，所有核都在总线上**监听（嗅探 snoop）**所有内存相关的事务。

触发失效的**不是**"Core1 在自己缓存里找到了 y"，而是：

1. Core1 根据内存地址发起写请求；
2. 请求被**广播到总线上**；
3. Core0 嗅探到该地址，与本地缓存行的 **Tag（内存高位地址）** 匹配；
4. 认出"这条缓存行归我持有、还是 M 态" → 触发"回写 + 失效"流程。


- **为什么 Core1 不能只拿 y 的 4 字节？**
  因为缓存的传输最小粒度就是整条缓存行（64B），协议状态也是以整条缓存行为单位管理的，不支持更小的粒度单独传输。
- **为什么这么设计？**
  缓存行机制牺牲了一点空间利用率，换来了极高的传输效率和简单的一致性管理——这是硬件权衡的结果。

> Core1 本地缓存里确实没有 y，是它的内存访问请求被广播到总线，Core0 嗅探到地址匹配，发现自己独占持有这一整条缓存行，从而触发失效流程。

## 5. 真共享 vs 伪共享

| | **True Sharing（真共享）** | **False Sharing（伪共享）** |
| --- | --- | --- |
| 场景 | 多个核读写**同一个变量** | 多个核读写**完全无关的不同变量** |
| 竞争来源 | 业务本身就需要共享该数据 | 只是恰好挤在同一条缓存行 |
| 本质 | 同步是**必须的** | 同步是**多余的、纯硬件层面的意外** |
| 处理 | 用锁/原子操作，开销合理 | 用 padding/对齐隔离，可以彻底消除 |

---

## 6. 伪共享的危害

- **大量缓存一致性流量（cache coherence traffic）**：每个核写一次，都要广播失效、回写主存、重新拉取整行；
- **缓存命中率暴跌**：本地副本频繁失效，等于"缓存形同虚设"；
- **多核提速上不去，甚至比单核还慢**：核越多，互相"踩踏"越严重；
- **高并发计数器、统计指标、多线程状态结构体**是重灾区。

---

## 7. 怎么解决：把变量拆到不同缓存行

核心思路只有一句话：**让经常被不同核独立修改的热变量，不要落在同一条缓存行里。**

{% asset_img false-sharing-solution.svg 伪共享解决方案对比图 %}

### 方法一：手动填充（padding）

```c
struct Data {
    int a;
    char pad[60];   // 补齐 64 字节，把 b 推到下一条缓存行
    int b;
};
```

`int a` 占 4 字节，填充 60 字节，保证 `b` 从下一条缓存行开始。

### 方法二：C++17 标准对齐（推荐，可移植）

```cpp
#include <new>

struct Stats {
    alignas(std::hardware_destructive_interference_size) uint64_t a;
    alignas(std::hardware_destructive_interference_size) uint64_t b;
};
```

- `std::hardware_destructive_interference_size` 是标准库提供的**建议对齐值**（通常等于缓存行大小，如 64），用于**主动破坏共享**（destructive interference）；
- `alignas` 强制变量起始地址按该值对齐，让 `a`、`b` **各自独占一条缓存行**；
- 配套还有一个 `std::hardware_constructive_interference_size`，用于**倾向于放同一条缓存行**（预取友好）的场景。

### 方法三：内存布局拆分

不要把多个线程独立修改的热变量塞进同一个结构体；拆成独立分配，或按线程分块。

## 8. 现代 C++ 会自动填充吗？

**不会。** 这是高频误区，重点讲清楚：

### ① 编译器会自动填充，但只为了"类型对齐"

```cpp
struct S {
    char c;   // 1 字节
    int  i;   // 4 字节，要求 4 字节对齐
};
```

编译器会在 `c` 后面自动塞 3 字节 padding，让 `i` 的地址 4 对齐。**这是满足 CPU 访问对齐要求和 ABI 布局规则**，跟缓存行、伪共享毫无关系——`c` 和 `i` 大概率仍在同一条缓存行里。

### ② `hardware_destructive_interference_size` 不是"自动开关"

它是一个**常量**，告诉你推荐的对齐大小，**不会改变 struct 的默认布局**。编译器不会看到"两个变量被不同线程写"就自动加隔离——它**根本不知道业务语义**，无法判断：

- 这两个变量是"不同核独立写，需要隔离"？
- 还是"本来就该一起访问，放一起更好"？

强行自动加 padding 会：增大内存占用、破坏 ABI、破坏网络协议/持久化结构的既有布局。所以标准把它留给程序员显式声明。

### ③ `thread_local` 也不能自动避免伪共享

`thread_local` 只是让每个线程各有一份副本，**不保证跨缓存行隔离**——多个线程局部变量在内存里依然可能紧挨着，落在同一条缓存行里照样伪共享。

### ④ 工程小结

| 想要的效果 | 怎么做 |
| --- | --- |
| 默认布局 | 编译器只做**类型对齐 padding**，不做**缓存行隔离 padding** |
| 规避伪共享 | **程序员显式控制**：`alignas(hardware_destructive_interference_size)` 或手动 padding |
| 检测 | 靠 perf / VTune 等性能工具，编译器不会自动检测 |

## 9. 常见误区澄清

1. ❌ **"伪共享是数据竞争，会导致内存错乱"**
   ✅ 不是！MESI 保证数据**正确**。伪共享**不会产生 bug，只会拖慢速度**——程序结果没错，就是跑得巨慢，是纯性能问题。

2. ❌ **"只要结构体有 padding 就不会伪共享"**
   ✅ 默认 padding 只是满足类型对齐（比如 int 要 4 对齐），量很小，变量依然在同一个缓存行。**默认 padding ≠ 防伪共享 padding。**

3. ❌ **"`thread_local` 天然避免伪共享"**
   ✅ 每个线程一份副本，但副本之间可能紧挨着，依然可能共享缓存行。

4. ❌ **"只读变量也会伪共享"**
   ✅ 不会。多个核同时**读**，缓存行处于 S（共享）态，不需要失效。**伪共享只在"多个核分别写同一条缓存行内不同变量"时出现。**

> 一句话判断标准：**写 + 同缓存行 + 写的不是同一个变量 = 伪共享。**

## 10. 怎么发现程序里有伪共享

多核并行程序出现这些现象时，值得怀疑：

- **线程越多，加速比越差，甚至变慢**；
- 每个线程操作的数据逻辑上完全独立（无锁、无原子竞争），性能却依然很差；
- 用 `perf` / Intel VTune 观察：存在大量 **cache coherence / cache invalidation** 事件、缓存行迁移频繁。

典型检查手段：

```bash
# Linux 下用 perf 观察缓存一致性相关事件
perf stat -e cache-misses,cache-references ./your_program
```

也可以直接做对照实验：给热变量加上 `alignas(64)` 隔离后重新跑，如果性能显著提升，基本就是伪共享。
