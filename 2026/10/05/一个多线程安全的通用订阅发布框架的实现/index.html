观察者模式

一个多线程安全的通用订阅发布框架的实现

2026-10-05 #观察者模式#设计模式

在企业开发中经常需要用到观察者模式：一些对象（Observer）作为观察者，对目标对象（Subject）的某些变化感兴趣,当变化发生时，Observer 需要及时获得通知，以便迅速做出改变或执行某些操作。

如果把这套“订阅—通知”的逻辑直接散落在业务代码里，很快就会遇到三个麻烦：订阅列表由谁维护、观察者销毁后留下的悬垂指针怎么处理、回调执行过程中又去注销自己导致死锁怎么办。本文实现一个通用的线程安全订阅通知框架 Notifier，并给出一个可编译运行的完整示例，说明如何在业务代码中低成本复用它。

一、设计目标

动手前先明确四条约束，后文的每个设计细节都是为它们服务的：

  • 线程安全：注册、注销、广播可能发生在任意线程，所有共享数据都要用互斥锁保护。
  • 生命周期安全：事件中心不“拥有”观察者。观察者销毁后自动脱离，既没有悬垂指针，也不会因为事件中心持有 shared_ptr 而导致对象永远无法释放。
  • 低侵入：被观察者只需继承模板并在事件发生时调用一次广播。观察者只需实现自己的回调接口，不依赖被观察者的具体类型。
  • 可复用：失效清理、加锁快照、参数转发这些容易写错的“脏活”只写一遍。

二、核心实现：Notifier 模板

接口一览

成员 访问级别 作用
registerCallback() public 注册观察者（传入 shared_ptr），内部自动去重
unRegisterCallback() public 主动注销观察者
getRegisteredCallbacksCount() public 当前注册数量，便于调试与测试
fireNotification() protected 向所有存活观察者广播事件
potentiallyFireNotification() protected 带 shouldFire 谓词的条件广播
callbackErased() protected virtual 观察者失效时的清理钩子，供子类同步旁路数据
removeExpiredCallbacks() private 清理失效 weak_ptr 并返回存活快照

三个关键设计

1. 只保存 weak_ptr，事件中心不拥有观察者。
注册时接收 shared_ptr，存储时转成 weak_ptr。观察者的生死由其创建者决定，事件中心只是一个“通讯录”。通讯录里某一项失效了，广播时顺手划掉即可，不会延长任何对象的生命周期。

2. 先加锁快照，再解锁广播。
removeExpiredCallbacks() 在锁内完成三件事：拷贝存活项、清理失效项、回写容器。锁释放之后才开始遍历快照执行回调。这样即使回调内部又去注册、注销自己或他人，也不会出现 std::mutex 重入死锁，更不会踩到迭代器失效的未定义行为。

3. 参数转发按观察者数量切换策略。
只有一个观察者时可以放心完美转发，支持 move-only 参数、零拷贝。有多个观察者时退化为 to_const_ref_or_copy——左值传 const 引用、右值拷贝一份，避免第一个回调把右值“消费”掉之后，后续观察者拿到被掏空的数据。

扩展点：条件广播与清理钩子

potentiallyFireNotification() 把“通知谁”的过滤逻辑以 shouldFire 谓词的形式下放给子类，而快照、清理、加锁、lock() 保活这些共性逻辑仍由基类统一负责。callbackErased() 则给维护了旁路数据结构的子类（例如按 key 建索引的通知器）留了一个同步清理的时机，调用时锁已被持有，实现中不要再加锁。

3.4 示例要点

  • 被观察者极薄：Horse 里没有锁、没有容器、没有生命周期管理，新增事件就是新增一个成员函数。
  • 接口隔离：观察者只依赖 IHorseCallback，既不需要继承 Notifier，也不需要知道 Horse 的存在，可以自由复用、单独测试。
  • 所有权清晰：Horse 不拥有观察者。观察者无论是 UI 面板、缓存对象还是临时对象都无所谓，谁创建谁持有，销毁即自动脱离。
  • 线程安全：多个线程同时调用 jump()/eat()/sleep() 与 registerCallback()/unRegisterCallback() 都是安全的。回调执行期间不持锁，回调内部再注册或注销也不会死锁。

五、小结

Notifier 把订阅通知中最容易出错的部分——生命周期、并发、参数语义——一次性封装干净，业务侧只剩下“表达事件”和“处理事件”两件事。落地时记住三条约定即可：

  1. 观察者一律用 shared_ptr 持有，注册后不必手动注销，销毁即自动脱离。
  2. 广播只在事件发生的线程上同步执行，回调里不要做长时间的阻塞操作。确需耗时处理时，转投到自己的线程池。
  3. 需要按类型、按兴趣定向通知时，优先扩展 shouldFire 谓词，而不是在子类里直接操作 mCallbacks。
